# Core Capacitor error catalog

This catalog covers `tapp-capacitor-sdk` `0.1.0-alpha.2`. Each row is one explicit throw, rejection, or error-result source site in the wrapper or its mapping, including shared helpers. The [JSON catalog](errors.json) contains the same entries, source lines, timing, and recovery guidance. Runtime messages are copied unchanged; variable native messages are identified as patterns. `null` in the code column means the wrapper assigns no code.

`reject` means a rejected JavaScript Promise. `resolve-error` means a fulfilled Promise containing `{ error: true, message }`. `throw` records an explicit source throw: web throws become Promise rejections through async public methods; Android cancellation rethrows stay inside native coroutines. Always catch rejections and check `data.error` before routing a fulfilled link-data result.

## Validation and startup decision tree

- `shouldProcess({ url })` and `fetchLinkData({ url })`: validate the URL first on every platform. Invalid input always rejects `INVALID_URL`, even before `start()`.
  - With a valid URL, `shouldProcess` works before startup. iOS returns the SDK boolean; Android returns the SDK boolean or `{ value: false }` if the SDK throws; web returns `{ value: false }`.
  - With a valid URL, native `fetchLinkData` before startup resolves `{ error: true, message: "Tapp has not been started. Call start() first." }`. After startup, SDK/backend failures resolve error data (except Android coroutine cancellation as cataloged below). Web always resolves unsupported-platform error data.
- `fetchOriginLinkData()` takes no URL. Before native startup it resolves the same error data; after startup SDK/backend failures resolve error data (with the same cancellation exception). Web always resolves unsupported-platform error data.
- Native `url` and `handleTappEvent`: check startup first and reject `NOT_STARTED` before validating method arguments. After startup, validate arguments and call the SDK. On web, both reject `UNIMPLEMENTED` regardless of startup or arguments.
- Native `start`: validate only until the first successful start; subsequent calls resolve without revalidation. Web validates every call and never initializes a native SDK.

**Whitespace difference:** iOS accepts whitespace-only `authToken` and `tappToken` at its validation guard; Android and web reject them. iOS also accepts a whitespace-only `influencer` at its guard; Android rejects it. Supply nonblank configuration on every platform. Acceptance by a wrapper guard does not establish that credentials are valid.

URLs are trimmed, require a scheme, and block `javascript:`, `data:`, and `file:` case-insensitively. Platform URL parsers can differ on edge cases such as `https://x/a b`, `https://`, and `tapp:`. See the [README Errors table](../README.md#errors) and [public API comments](../src/definitions.ts).

## Failure handling

Load `authToken` and `tappToken` from app configuration for the same dashboard app and match their issuing environment to `env`. Await `start()` before dependent native calls, check network access, and use the cause and fix for the relevant row. `START_ERROR`, `HANDLE_EVENT_ERROR`, and some `URL_ERROR` messages do not yet describe recovery; the fix column provides checks without changing those runtime messages. Do not log credentials or arbitrary SDK error text that could contain sensitive configuration. Set `loggingBehavior: 'none'` in `capacitor.config.ts` to prevent bridge argument logging.

Native `didFailResolvingURL` is a separate listener event, not a Promise rejection or `{ error: true }` result. iOS emits `{ url, error: error.localizedDescription }` at [TappPlugin.swift:157](../ios/Sources/TappCapacitorPlugin/TappPlugin.swift#L157); Android emits `{ url: response.url, error: response.error }` at [TappPlugin.kt:35](../android/src/main/java/so/tapp/capacitor/TappPlugin.kt#L35). No wrapper code is assigned. Handle the event as a resolution failure and check configuration, network, and incoming-link setup in the README. Android's `deferredLinkReceived` also uses the link-data mapping and can carry `error: true` from an SDK response.

Mapping helpers construct the payloads for the listed call sites: iOS `TappMapping.failure` at line 80; Android `TappMapping.error` at line 102. They do not add rejection codes. Android message filtering and fallback text are recorded with each affected site. Invalid metadata is silently dropped; a missing or blank custom event name falls back to `custom_event_autogenerated`, so neither produces a separate error.
